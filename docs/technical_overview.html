What the System Does

Garmin Coach is a local web application — it runs entirely on your own computer, not on any cloud server. You open it in a browser at localhost:8000, but all data stays on your machine.

In one sentence: it ingests your Garmin running and cycling data, stores it permanently, visualises your training history per sport, and uses the Claude AI to generate personalised weekly plans and answer coaching questions.

Core capabilities

  • Today dashboard — the landing view (§14): last night's readiness, today's planned session, energy balance (eaten vs burned), and training load (run + ride) vs recovery, pulled from every domain into one glance
  • Redesigned UI — a light theme with a left sidebar and clean line-icon navigation, replacing the old dark top-tab layout
  • Multi-sport data ingestion — imports Garmin CSV exports (manual) or automates the export via a real Chrome browser; one sync session pulls both running and cycling
  • Deduplication — importing the same file twice never creates duplicate entries
  • Running tab — weekly mileage, running load (TRIMP), ACWR with its 0.8–1.3 safe band, and personal records
  • Cycling tab — weekly distance, speed trend, heart-rate trend, and an aerobic-efficiency trend (kept fully separate from running so neither pollutes the other)
  • AI weekly plan — agree a week with the coach in conversation, then one click structures it into a saved Mon–Sun calendar shown right below the chat (one plan at a time)
  • AI coaching chat — a tool-use conversation grounded in your live activity, sleep, and nutrition data
  • Goals & fitness tracking — race targets plus an aerobic-efficiency trend (speed ÷ heart rate over time)
  • Sleep tab — per-night detail (deep/light/REM stages, HRV, recovery metrics) over a weekly long-term backdrop, each with its own sync button (nightly vs the 1-year history)
  • Calories tab — daily calories burned (resting + active), scraped from Garmin's table (no CSV export exists for it)
  • Food / nutrition agent — a second Claude agent: tell it what you ate (text or photo) and it logs each item, builds a personal food library, and tracks daily protein/fat/carbs/kcal
  • Holistic coach — the running coach factors in cycling load, sleep recovery, and food intake (energy in vs out), steered by an editable plain-English preferences file
💡
Why local? Garmin does not offer a public API for personal use. Running locally means no cloud fees, no third-party data sharing, and no rate limits. Your 873 runs, 280 rides, and all AI responses stay on your machine.

Backend — FastAPI

FastAPI is the Python web framework that handles every HTTP request — from serving the HTML page to answering chart data queries to running the Garmin sync. It is chosen for its speed, automatic API documentation, and typed Python support.

The app is started with uvicorn (a lightweight async web server). The --reload flag makes the server restart automatically when any .py file changes — essential during development.

backend/main.py — entry point
from fastapi import FastAPI

app = FastAPI(title="Garmin Coach")

# Each router is a separate file of related endpoints.
# This is called "separation of concerns" — each file has one job.
app.include_router(activities_routes.router)
app.include_router(stats_routes.router)
app.include_router(plans_routes.router)
app.include_router(chat_routes.router)

@app.get("/", response_class=HTMLResponse)
def index():
    # Serve the single HTML file that is the entire UI
    return HTMLResponse(html_path.read_text())

Database — PostgreSQL

PostgreSQL is a production-grade relational database. We chose it over simpler alternatives (like SQLite or a plain JSON file) for two reasons: it handles concurrent reads/writes cleanly, and it supports JSONB — storing JSON objects inside a table column, which we use for the raw Garmin data and weekly plans.

Connection pooling

Instead of opening and closing a database connection on every HTTP request (slow), a connection pool keeps 2–10 connections permanently open and ready. When the app needs the database it borrows one, uses it, and returns it.

backend/db.py — pool setup
# min_size=2: always keep 2 connections open and ready.
# max_size=10: never open more than 10 at once.
_pool = ConnectionPool(
    conninfo=config.DATABASE_URL,
    min_size=2,
    max_size=10
)

Deduplication — the most important design decision

When you re-import the same CSV, or export a CSV that overlaps with a previous one, the database must not create duplicate entries. We solve this with an upsert:

The upsert pattern
INSERT INTO activities (id, start_local, distance_km, ...)
VALUES (...)
ON CONFLICT (start_minute) DO UPDATE SET
    distance_km = COALESCE(excluded.distance_km, activities.distance_km),
    avg_hr      = COALESCE(excluded.avg_hr,      activities.avg_hr),
    ...

start_minute is the run's start time truncated to the minute (e.g. "2026-06-04 07:32"). Since two real runs can never start in the exact same minute, this is a reliable unique key. If a conflict is detected, COALESCE keeps whichever value is not null — so a richer earlier import (with HR data) is never overwritten by a sparser later one.

✅
Result: Importing many overlapping CSVs (thousands of rows across two years) collapses to exactly the genuinely-new activities — currently 873 runs + 280 rides — with no duplicates and no data loss.

One table, two sports — the discriminator pattern

Running and cycling share the same shape (distance, duration, HR, calories, elevation), so they live in one activities table. The only field that differs — pace (min/km) vs speed (km/h) — gets its own column, and a single activity_type column routes each row. Every running query carries WHERE activity_type = 'running' and every cycling query = 'cycling', so the two sports are fully isolated in the UI while sharing all the storage, dedup, and import machinery.

CSV Importer

Garmin exports CSVs in several shapes depending on language and on whether the file was re-saved through (Greek) Excel. The importer detects the actual number/date format from the data itself — not from the header language — then categorises each row as running or cycling.

FeatureRaw export (EN or GR)Greek-Excel re-save
Decimal separator14.32 (period)14,32 (comma)
Date format2026-06-11 17:37:51 (ISO)11/6/2026 17:37
Time format00:35:07 (clean)5:30:00 πμ (time-of-day + πμ/μμ)
Sport metricrunning → Μέσος ρυθμός (pace) · cycling → Μέση ταχύτητα (speed)
⚠️
The trap we avoided: the cycling file had Greek headers but ISO/period numbers. The old header-based detection would have read 14.32 km as 1432 km. Detecting the format from the values fixes this.
backend/csv_importer.py — format detection from data + sport routing
def _detect_excel_greek(rows, header_info):
    # Look at the actual values, not the header language.
    for row in rows:
        # πμ/μμ in a time field ⇒ Excel re-save (comma decimals)
        if any(ch in time_value for ch in ("π", "μ")): return True
        if date_value.startswith("20"):  # ISO date ⇒ raw export
            return False
    return False

def _activity_category(activity_type):
    # 'Ποδηλασία' / 'Cycling' → cycling ; 'Τρέξιμο' / 'Running' → running
    t = activity_type.lower()
    if "ποδηλασ" in t or "cycling" in t: return "cycling"
    if "τρέξιμο" in t or "running" in t: return "running"
    return None  # skip swims, walks, etc.

Synthetic IDs

Garmin's CSV format does not include a unique activity ID (unlike the API). We generate a deterministic ID by hashing the date + distance + duration. The same run always produces the same hash, making re-imports safe. IDs are made negative to distinguish them from real Garmin API IDs (which are positive).

Deterministic ID generation
def _synthetic_id(date_str, distance_km, duration_min):
    payload = f"{date_str}|{distance_km}|{duration_min}".encode()
    h = hashlib.sha256(payload).hexdigest()[:15]  # 60-bit hash
    return -int(h, 16)  # negative = CSV-sourced

Playwright Sync — Browser Automation

Playwright is a browser automation library from Microsoft. It can control Chrome, Firefox, or Edge programmatically — clicking buttons, filling forms, and capturing downloads — exactly as a human user would.

🔒
Why not the official Garmin API? Garmin's developer program is B2B-only — it requires a registered company and a formal application process. Browser automation against the same website you log into manually was the original path.
⚠️
This section is now legacy. Sleep, running, cycling, and calories all sync through Garmin's internal web JSON API instead — see §6B. This browser path is kept only for the manual "Import CSV" upload and as a documented fallback.

The persistent profile strategy

A fresh browser profile with no history, no cookies, and no saved preferences looks like a bot to Garmin's login system. We use a persistent profile stored in data/chrome_profile/ that survives between runs. After the first login the session is reused automatically.

backend/garmin_playwright.py — anti-detection
# 1. Use the real Google Chrome installed on your machine (not a downloaded browser)
# 2. Point to a persistent profile directory that builds up history over time
# 3. Pass --disable-blink-features=AutomationControlled so Chrome does NOT
#    set the navigator.webdriver flag that Garmin checks
context = pw.chromium.launch_persistent_context(
    user_data_dir="data/chrome_profile",
    channel="chrome",
    headless=False,
    args=["--disable-blink-features=AutomationControlled"],
)

# 4. Inject JS into every page before it loads — overrides navigator.webdriver
context.add_init_script(
    "Object.defineProperty(navigator, 'webdriver', {get: () => undefined})"
)
🔀
Two sync buttons, one engine. export_activities(sports) exports a CSV for each requested sport in a single browser session. The Running tab's Sync Running button asks for ["running"] (fast); the Cycling tab's Sync from Garmin asks for ["running", "cycling"]. The first sport exports with no extra page reload; only switching to the second sport's filter pays the reload cost — so single-sport syncs stay quick.

def _wait_for_export_button(page, timeout=45_000):
    # Try each locale label in turn
    for label in ["Εξαγωγή σε CSV", "Export to CSV", ...]:
        try:
            loc = page.get_by_text(label, exact=True)
            loc.first.wait_for(state="visible", timeout=per_label)

    # Fallback: any button or link containing the text "CSV"

Garmin API Sync — the Current Path

Every Sync button now reads from Garmin Connect's internal web JSON API (the same endpoints Garmin's own website calls) instead of driving a browser. It logs in once with the garminconnect library, caches the OAuth token, and then pulls clean JSON straight from connectapi.garmin.com — no page rendering, no export button to hunt for, nothing to break when Garmin's UI changes.

🩺
What forced the change. Garmin's /app/sleep web page began serving a "Looks Like We Crashed" render error server-side — it never even fetches the sleep data before failing, so there was nothing for the browser scraper to read. The API returns that same data reliably, so sleep moved first; running, cycling, and calories followed for consistency and richer data.
✅
What the API gives that the browser CSV never could. Real Garmin activityIds (not synthetic hashes), VO2max (absent from the CSV — this was the "dashboard shows 56, watch shows 58" gap), HR-zone time, training effect, and — for sleep — HRV, body battery, respiration and stress, all in one call.

The client & token cache

backend/garmin_api.py owns a single logged-in client. One login(token_dir) call does both jobs: if a saved token exists it resumes with no network login; otherwise it authenticates with the .env credentials and persists the token to data/garmin_tokens/ for next time. The client is also cached in-process, so a burst of syncs shares one session.

backend/garmin_api.py — log in once, then reuse
def _client():
    if _client_cache is not None:
        return _client_cache                 # in-process reuse
    g = Garmin(config.GARMIN_EMAIL, config.GARMIN_PASSWORD)
    mfa, _ = g.login(str(config.GARMIN_TOKEN_DIR))  # resume OR login+persist
    if mfa:
        raise RuntimeError("MFA code needed — clear it once in a browser login")
    _client_cache = g
    return g
⏳
Rate limits apply to logins, not data. Garmin throttles repeated logins (a burst returns 429, then 401 "Failed to retrieve social profile" for ~15–60 min). Because the token is cached, the app logs in once and resumes forever after — the get_sleep_data / get_activities / get_stats reads themselves are not the limited part.

Activities: how the JSON becomes a row

Garmin has many sport sub-types; they're folded into the two families the app tracks. Pace is derived for runs and speed for rides, straight from distance and duration. The full raw JSON is kept in raw_json for later use (HR zones, training effect).

backend/garmin_api.py — activity mapping (abridged)
def _activity_summary(a):
    family = _activity_family(a["activityType"]["typeKey"])  # run | cycle | skip
    dist_km = a["distance"] / 1000
    dur_min = a["duration"] / 60
    return {
        "id": a["activityId"],                 # REAL positive id
        "start_local": a["startTimeLocal"],
        "avg_pace_min_per_km": dur_min / dist_km if family == "running" else None,
        "avg_speed_kmh": dist_km / (dur_min / 60) if family == "cycling" else None,
        "vo2max": None,                          # enriched from get_max_metrics
        ...
    }
🔗
API rows upgrade CSV rows — they don't duplicate them. Both paths write through db.upsert_activity, which dedups on the start-minute and uses COALESCE while keeping the largest id (§4). A real positive Garmin id beats an old synthetic negative one, and VO2max fills in where the CSV left a blank — so an API sync silently enriches history imported earlier from CSV.

Both worlds, on purpose

The legacy paths are not gone. csv_importer.py still powers the manual Import CSV upload (drop in any Garmin export), and the Playwright modules (§6) remain on disk as a documented fallback. The API is simply the default the buttons use now.

Claude AI Integration

We use the Anthropic Python SDK in two ways: a shared tool-use loop that powers both agents — the holistic coach and the nutrition logger (§13) — and a one-shot structured-JSON call that turns the coach's plan into a calendar (later in this section). The agents call functions to read and write the local database rather than holding all the data in the prompt, so token cost stays roughly flat as the database grows.

One shared tool-use loop

Both agents run the identical loop, factored into backend/agent.py: send the conversation to Claude with a set of tools, run whatever tools the model asks for, feed the results back, and repeat until it returns plain text. Only the model, system prompt, tools and tool dispatcher differ — so the loop is written once instead of copied into each agent.

backend/agent.py — run_tool_loop (shared by coach + nutrition)
for _ in range(max_iterations):
    resp = client.messages.create(
        model=model, tools=tools, messages=messages,
        system=[{"text": system_text,
                 "cache_control": {"type": "ephemeral"}}],  # prompt cached
        **opts)                                   # coach adds thinking + effort
    messages.append({"role": "assistant", "content": resp.content})

    if resp.stop_reason == "tool_use":
        results = [run_tool(b.name, b.input) for b in resp.content
                   if b.type == "tool_use"]
        messages.append({"role": "user", "content": results})  # tool_result blocks
        continue
    return text_of(resp)        # end_turn → the final answer
⚡
A model matched to each job. The coach runs on Opus 4.7 (adaptive thinking, high effort) because training advice rewards deep reasoning; the nutrition agent runs on the faster Sonnet 4.6 — food logging is mostly lookup, arithmetic and confirmation, so the lighter model keeps replies snappy. The system prompt is constant across a turn, so it's cache_control-cached to cut both cost and latency.

The holistic coach — a tool-use agent

The coach is no longer running-only. It is a tool-use agent: rather than dumping every metric into the prompt, Claude is given a set of tools and decides which to call. This lets it pull only the data a given question needs, and reason across all of your training signals at once.

backend/coach.py — the coach's tools
get_recent_activities   # runs: distance, pace, HR, VO2max
get_recent_cycling      # rides: distance, speed, HR
get_recent_sleep        # nightly duration, stages, HRV
get_recent_calories     # energy BURNED (resting + active)
get_recent_nutrition    # energy EATEN (the four daily totals)
get_goals               # race targets + training goals
get_pr_progression      # personal-record history
get_training_load       # weekly TRIMP load + ACWR + HRV (§14–15)

With cycling, sleep, calories-burned and food-intake all on tap, the coach reasons about energy balance (eaten vs. burned), recovery (sleep + HRV before hard days), and cross-training load — not just the last few runs.

📝
coach_persona.md — a plain-English file you can edit. Its contents are loaded (load_persona()) and injected into the coach's system prompt, so you steer the coach's priorities (e.g. "running is the focus; weigh cycling and sleep as supporting context") in words, without touching code.

The weekly plan — structured straight from the conversation

There is no separate "generate a plan" screen any more. You settle on a week with the coach in ordinary conversation; when you're happy, one click on Save this week's plan (under the chat) sends the coach's most recent message to POST /plans/from-coach. That route asks Claude to convert whatever free-form prose the coach wrote into a strict 7-day JSON schema — the same structured-output trick as before, now sourced from the chat itself instead of a form.

backend/routes/plans.py — structure the coach's last message
# the newest assistant turn in the coach channel
last = next(m["content"] for m in reversed(history) if m["role"] == "assistant")

prompt = f"""Convert this free-text running plan into a strict 7-day week.
--- PLAN TEXT ---
{last}
Return ONLY JSON, no fences:
{{ "week_start", "summary", "weekly_km",
   "days": [ 7 × {{ "day", "date", "workout_type", "title", "description", ... }} ] }}"""

plan = json.loads(re.search(r'\{[\s\S]*\}', reply).group())
assert len(plan["days"]) == 7          # validate before saving

The result is saved to weekly_plans tagged source: "chat" and marked accepted — the single plan you agreed to — and any previous one is archived. It renders as a Mon–Sun calendar directly below the chat, and the Today dashboard reads the same plan for its "planned today" card. One conversation, one plan, one place.

Frontend — HTMX + Chart.js

The entire frontend is a single HTML file — no React, no Vue, no npm install, no build pipeline. For a personal local tool, the simplest approach that works is the correct one.

HTMX — server-rendered interactivity without JavaScript

HTMX is a small library (~14 KB) that lets HTML elements make HTTP requests and swap the server's response into the page — without writing any JavaScript. The server builds the HTML; HTMX handles the swap.

Chart.js — the per-tab charts

Charts use Chart.js 4.4.3 from a CDN. Each tab fetches its /stats/* endpoints in parallel with Promise.all() and renders together. Charts are lazy — each tab initialises only the first time it's opened (separate dashReady / cycReady / goalsReady flags), so nothing loads until you look at it. All charts share one styling source: a single PALETTE object plus Chart.defaults (font, muted axis colour, gridlines) set once, so every chart reads as a family — running blue, cycling purple, sleep indigo, calories amber — with one tooltip style throughout.

Lazy chart initialisation
let dashReady = false;

function showTab(id) {
    // Only fetch + render charts the first time Dashboard is opened
    if (id === 'dashboard' && !dashReady) {
        dashReady = true;
        initCharts();
    }
}

async function initCharts() {

The two tables

Parsing the 1-day file (key → value)

Unlike the row-based activity CSVs, the 1-day sleep file is a vertical list of key,value lines in Greek. The parser reads it into a dictionary and converts the localized values — durations like 6ώ 43λ → minutes, and so on.

backend/sleep_importer.py — the per-night parser
def parse_sleep_day(text):
    d = {}
    for line in text.splitlines():
        k, v = line.split(",", 1)        # "Διάρκεια βαθέος ύπνου,59λ"
        d[k.lower().strip()] = v.strip()
    return {
        "night_date":   d["ημερομηνία"],
        "deep_min":     _parse_duration(d["διάρκεια βαθέος ύπνου"]),
        "rem_min":      _parse_duration(d["διάρκεια ύπνου rem"]),
        "hrv_ms":       _parse_int(d["μέσο hrv στη διάρκεια της νύχτας"]),
        ...
    }

The Today Dashboard — Integrated Metrics

Every other tab answers one question about one domain. Today is the screen that reads across all of them — the only place that joins running, cycling, sleep, calories burned and food eaten into single answers. Each computed view below has its own /stats endpoint and is refetched on every visit.

Readiness

The lead card surfaces last night's sleep score, duration and HRV (from sleep_nights), colour-coded good / fair / low — a one-glance "should I go hard today?" read.

Energy balance — eaten vs burned

GET /stats/energy-balance joins the day's eaten calories (summed from food_log) with burned calories (the calories table) to give a daily net: negative = deficit (losing), positive = surplus (gaining). It renders as a diverging bar chart (deficit green, surplus red), anchored on the days you actually logged food, with each bar's eaten/burned breakdown on hover. A day with no Calories sync returns null instead of a misleading number, so it reads "pending" rather than a fake deficit. The running 7-day net is converted to an approximate fat change (7,700 kcal ≈ 1 kg).

Training load & recovery

The standout: GET /stats/training-load turns every run and ride into one comparable load number using Banister TRIMP — duration weighted by heart-rate intensity, so a hard hour counts far more than an easy one and the two sports finally share a single scale.

backend/training_load.py — TRIMP per session
HRr   = (avg_hr − resting_hr) / (max_hr − resting_hr)   # 0–1 intensity
TRIMP = duration_min × HRr × 0.64 × e^(1.92 × HRr)

# resting_hr ← averaged from recent sleep nights
# max_hr     ← the highest value ever recorded

Weekly load is stacked by sport (run + ride) and overlaid with the HRV recovery line from sleep on a second axis — the "are you absorbing your training?" picture: load climbing while HRV falls is the warning sign. Above the chart sits the acute : chronic workload ratio (ACWR) — this week's load ÷ the 4-week average — flagged green in the 0.8–1.3 sweet spot and red past 1.5, the classic overtraining / injury signal.

🏃
One engine, three consumers. The same training_load.compute() serves all of them, so the numbers can never disagree:
  • Today — no sport filter → the combined run + ride load (the systemic stress the body actually feels).
  • Running tab — ?sport=running → running-only TRIMP bars plus a rolling ACWR line (each week's load ÷ the mean of its previous 4 weeks) drawn against the 0.8–1.3 band. This replaced the old pace and heart-rate trend charts.
  • The coach — via its get_training_load tool (§7).
⚠️
Estimated inputs. TRIMP needs a max HR and a resting HR. The app estimates max HR from the highest value ever recorded (an underestimate if you've never truly maxed out) and resting HR from your sleep data. Absolute load values are therefore approximate — but the trend and the ACWR ratio hold regardless.
📅
The week starts Sunday. Every weekly bucket in the app — mileage, distance, load, efficiency trends — starts on Sunday to match the Garmin watch. Postgres' DATE_TRUNC('week', …) is hard-wired to Monday, so the app shifts the date +1 day, truncates, then steps back 1 day: a Sunday-aligned bucket from a Monday-only function. One Python helper (_week_start) and one SQL constant keep all six weekly aggregations in lockstep.

Scientific Basis — Why These Formulas

The training-load metrics (§14) aren't invented — they're established sports-science models. This section documents the reasoning and the references, so the choices are defensible rather than arbitrary.

Training load — Banister TRIMP

The goal is to turn a session into a single stress dose: not "how far" but "how much did this tax the body?" Two inputs drive that — how long and how hard — and TRIMP (TRaining IMPulse) combines them.

Intensity — heart-rate reserve (HRr). Hardness is measured relative to the individual using the Karvonen heart-rate-reserve method: the heart's usable band runs from resting to max, and HRr asks where the session's average sat within it.

HRr — Karvonen heart-rate reserve (0–1)
HRr = (avg_hr − resting_hr) / (max_hr − resting_hr)

Using the reserve (not avg_hr / max_hr) makes it personal — it accounts for both the floor and the ceiling, so HRr = 0.5 means the same relative effort for any athlete.

Banister TRIMP — the stress dose
TRIMP = duration × HRr × 0.64 × e^(1.92 × HRr)

The term 0.64 · e^(1.92·HRr) is an exponential weighting that makes hard time count disproportionately more. The justification is physiological: blood-lactate accumulation (and the metabolic/hormonal strain it tracks) rises exponentially, not linearly, with intensity. Banister fitted that exact curve to the lactate response, so the formula encodes how a real body's stress accelerates as you push harder. The constants are empirical and sex-specific: 0.64 & 1.92 for men, 0.86 & 1.67 for women.

🧮
Worked example (resting HR 48, max HR 204 → a 156-bpm reserve). The same 60 minutes, two intensities:
Sessionavg HRHRrTRIMP
Easy hour1200.46≈ 43
Hard hour1750.81≈ 149
Identical duration, but the hard hour is ~3.5× the load — exactly why TRIMP beats "time" or "distance" as a stress measure. Each session's TRIMP is summed per Sunday-week, split run vs ride.

Overtraining risk — acute : chronic workload ratio (ACWR)

ACWR
ACWR = this week's load ÷ 4-week average weekly load
       = acute (fatigue) ÷ chronic (fitness)

The key insight, from Gabbett's "training–injury prevention paradox": injury risk is driven less by how much you train than by how fast you change it relative to what you're adapted to. A high chronic base is protective; a sudden spike is dangerous. The thresholds the app uses come straight from that work:

ACWRZoneMeaning
< 0.8lowDetraining / returning from a break
0.8 – 1.3optimalThe sweet spot — building safely
1.3 – 1.5highCaution — load running ahead of base
> 1.5very highSharp injury / overtraining risk — pull back

Recovery — HRV

HRV (heart-rate variability, the beat-to-beat variation measured overnight, rMSSD-based) is a validated marker of parasympathetic (recovery) activity. Higher = better recovered; a downward trend signals accumulated fatigue, poor sleep, or illness. The app reads it against load (Plews et al.): rising load + falling HRV is the strongest "back off" signal, because each confirms the other from a different direction.

⚠️
Honest simplifications. The Garmin CSV gives only per-session averages, not the second-by-second heart-rate stream — so this is session-average TRIMP, not the more precise zone-weighted or per-beat variant. Max HR is estimated from the highest value ever recorded (an underestimate if never truly maxed), and resting HR is averaged from sleep. Absolute load values are therefore approximate; the trend and the ACWR ratio are the trustworthy outputs.
💾
Where these numbers live. TRIMP and ACWR are not stored — there is no load table. They're derived, recomputed on demand in backend/training_load.py from the raw rows that are stored: activities with heart rate (activities) and resting HR / HRV (sleep_nights). That one module is shared by the Today chart (GET /stats/training-load) and the coach's get_training_load tool, so the dashboard and the AI read identical figures.

  • Morton RH, Fitz-Clarke JR, Banister EW. Modeling human performance in running. J Appl Physiol, 1990;69(3):1171–77. — the impulse–response model.
  • Gabbett TJ. The training–injury prevention paradox. Br J Sports Med, 2016;50(5):273–80. — ACWR & the 0.8–1.3 sweet spot.

The MCP Coach — Chatting With Your Data

The in-app coach (§7) calls the paid Anthropic API once per message. To get the same data-grounded coaching for a flat subscription fee instead of per-message cost, the app also exposes your data to the ordinary Claude Desktop chat through a local MCP server.

🔌
What is MCP? The Model Context Protocol is an open standard for giving an AI assistant access to outside data and actions. The assistant itself has no hands — it can only produce text. An MCP server runs on your machine and offers a set of tools (named functions, each with a description). The assistant decides when to call a tool, the server runs it and returns the result, and the assistant grounds its answer in that result. Here the tools are read-only queries against your local Garmin database.

The server — mcp_coach.py

A small local server registered in Claude Desktop's claude_desktop_config.json under mcpServers. Claude Desktop starts it on launch and talks to it over stdin/stdout — there is no network port and nothing is exposed online. It reuses the in-app coach's own data functions (backend.coach._run_tool), so the two never drift apart, and it only needs the local PostgreSQL running (independent of the web app).

mcp_coach.py — a tool is just a described function
server = MCPServer("garmin-coach", instructions=COACHING_CONTEXT)

@server.tool()
def training_load() -> str:
    """Weekly TRIMP load + the ACWR overtraining ratio, with HRV and resting HR."""
    return coach._run_tool("get_training_load", {})

# … and run it over stdio
server.run("stdio")

The Weekly Fitness Report — Automation

Every Sunday ~10:00 a multi-page PDF lands in the Downloads folder: Overview · Weekly Review (recovery, nutrition, and a detailed running progression analysis + a goal-driven coaching verdict) · the detailed Monday–Saturday plan (warm-up / main / cool-down with adaptive HRV gates) · Sleep · Nutrition — all built from the local database, with the written analysis and plan produced on the subscription (no API cost).

📅
The running week is Monday–Saturday. Saturday is the long run and Sunday is the day off (and the day the report runs). So the Sunday report reviews the Monday–Saturday that just finished and plans the next Monday–Saturday (six training days).

The hybrid design — charts by code, words by Claude

A background script can draw charts but can't write insightful coaching; a chat can reason but can't reliably render a polished PDF. So the two are split:

  • fitness_report.py — a Python generator that reads the database, draws every infographic (training-load bars, HRV trend, the aerobic-efficiency trend, sleep stages, burned-vs-eaten, macros) with native vector drawing (fpdf2, no heavy chart library), and renders the pages.
  • data/report_ai.json — the written half: the verdict, the per-page feedback, the progression commentary + comparison table, and the structured plan. The generator renders whatever this file holds (with a rule-based fallback if it is missing).
📈
Progression analysis. The heart of the Weekly Review. It draws an app-style Aerobic Efficiency Trend — one faint dot per run plus a bold weekly-average line over the full history, where efficiency = speed (km/h) ÷ HR × 100 (higher = fitter at the same effort). Below it, a comparison table matches this week's runs to comparable past runs (same distance / HR) with colour-coded verdicts, and a written breakdown judges endurance, speed and VO2max separately. A flat efficiency line while under-fuelling reads as fatigue, not lost fitness.
🎯
Every report is one step closer to the goal. A "Toward your goals" section gives a verdict on whether the week's runs were good or bad relative to the goal trajectory (the Nov 15 5k and Dec 20 half), states where the athlete stands versus each target, sets the next concrete targets, and the plan is adjusted from the measured progression — progress the stimulus when efficiency and paces improve, consolidate when HRV, fuel or ACWR say to. This guiding principle is written into the scheduled task's own instructions.
🏋️
The weekly training template — 3 quality runs + 2 strength + recomp nutrition. The athlete's goals, in priority order, are baked into every plan: (1) get faster (5k first), (2) build the distance into the half, (3) lose fat and add some muscle for a leaner, athletic physique (a recomposition, not bodybuilding). The six training days follow a fixed, evidence-based shape:
  • Mon easy recovery · Tue track Q1 (5k/VO2) · Wed easy · Thu track Q2 (10k/threshold) · Fri easy / cross-train · Sat long run with a progressing half-marathon-pace block (which replaces a stand-alone tempo and grows ~3 km → 8–10 km over the weeks). Max three quality run days, spaced ~48 h; Sunday is the only full rest.
  • Two runner-strength sessions, placed on the hard-run days so the easy days and Sunday stay true recovery (minimising concurrent-training interference): Tue heavy lower body + plyometrics (power & running economy), Thu upper body + posterior chain (the athletic build). Heavy, low-rep, never to failure — not hypertrophy "pump" work. No third lifting day; Fri carries no lifting to keep the legs fresh for Saturday.
  • Nutrition is a gentle, periodised deficit — not "eat more everywhere". The three hard days are fuelled at maintenance-plus (carbs around the session); the easy days hold a modest ~300–500 kcal deficit; protein stays near ~2 g/kg every day. That drives slow fat loss (~0.25–0.4 kg/week) while speed keeps climbing — a larger deficit would cost the 5k before it costs the scale.
Volume targets 60–70 km but ramps ≤~10%/week, with a recovery week roughly every fourth or whenever ACWR >~1.4 or HRV is suppressed. The whole template is encoded in the scheduled task's instructions, so every Sunday report reproduces it automatically.

Desktop Launch & Polish

The app is launched by start_app.bat, which starts the uvicorn server and opens it in a clean Edge/Chrome app window. Two small fixes make that feel like a real desktop app.

Wait for the server before opening the browser

The launcher used to open the browser on a blind timeout /t 3. But uvicorn with --reload plus the database pool often needs longer than three seconds, so the browser arrived first and showed ERR_CONNECTION_REFUSED (and a stray cmd window flashed up to do the opening). Now a tiny hidden helper, scripts/open_when_ready.ps1, polls port 8000 and opens the browser only once the server actually answers — no race, no refused page, no extra window.

start_app.bat — launch the opener hidden; it waits for the port
:: opens the browser only once the server is listening (polls :8000), runs hidden
start "" /b powershell -NoProfile -ExecutionPolicy Bypass -WindowStyle Hidden ^
      -File "%~dp0scripts\open_when_ready.ps1"

.venv\Scripts\python.exe -m uvicorn backend.main:app --reload

A real app icon, not the generic globe

An Edge/Chrome app-mode window takes its taskbar icon from the page's favicon. The page had none, so Windows showed a generic globe. The app now serves the existing runner icon at /favicon.ico and links it in the page head, so the tab and the taskbar window show the runner. (Chrome/Edge cache the app-window icon, so it updates on the next launch.)

backend/main.py — serve the icon
@app.get("/favicon.ico", include_in_schema=False)
def favicon() -> FileResponse:
    return FileResponse("assets/runner.ico", media_type="image/x-icon")
