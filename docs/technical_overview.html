What the System Does

Garmin Coach is a local web application — it runs entirely on your own computer, not on any cloud server. You open it in a browser at localhost:8000, but all data stays on your machine.

In one sentence: it ingests your Garmin running and cycling data, stores it permanently, visualises your training history per sport, and uses the Claude AI to generate personalised weekly plans and answer coaching questions.

Core capabilities

  • Multi-sport data ingestion — imports Garmin CSV exports (manual) or automates the export via a real Chrome browser; one sync session pulls both running and cycling
  • Deduplication — importing the same file twice never creates duplicate entries
  • Running tab — weekly mileage, pace trend, heart-rate trend, personal records
  • Cycling tab — weekly distance, speed trend, heart-rate trend (kept fully separate from running so neither pollutes the other)
  • AI weekly plans — generates a structured 7-day plan, or turns a plan you paste from the coach chat into a saved Mon–Sun calendar
  • AI coaching chat — streaming conversation with real-time context from your activities
  • Goals & fitness tracking — race targets plus an aerobic-efficiency trend (speed ÷ heart rate over time)
  • Sleep tab — per-night detail (deep/light/REM stages, HRV, recovery metrics) over a weekly long-term backdrop
  • Hands-off daily sleep sync — runs automatically at logon and grabs last night's sleep, once per day, with no clicking (see §12)
💡
Why local? Garmin does not offer a public API for personal use. Running locally means no cloud fees, no third-party data sharing, and no rate limits. Your 873 runs, 280 rides, and all AI responses stay on your machine.

Backend — FastAPI

FastAPI is the Python web framework that handles every HTTP request — from serving the HTML page to answering chart data queries to running the Garmin sync. It is chosen for its speed, automatic API documentation, and typed Python support.

The app is started with uvicorn (a lightweight async web server). The --reload flag makes the server restart automatically when any .py file changes — essential during development.

backend/main.py — entry point
from fastapi import FastAPI

app = FastAPI(title="Garmin Coach")

# Each router is a separate file of related endpoints.
# This is called "separation of concerns" — each file has one job.
app.include_router(activities_routes.router)
app.include_router(stats_routes.router)
app.include_router(plans_routes.router)
app.include_router(chat_routes.router)

@app.get("/", response_class=HTMLResponse)
def index():
    # Serve the single HTML file that is the entire UI
    return HTMLResponse(html_path.read_text())

Database — PostgreSQL

PostgreSQL is a production-grade relational database. We chose it over simpler alternatives (like SQLite or a plain JSON file) for two reasons: it handles concurrent reads/writes cleanly, and it supports JSONB — storing JSON objects inside a table column, which we use for the raw Garmin data and weekly plans.

Connection pooling

Instead of opening and closing a database connection on every HTTP request (slow), a connection pool keeps 2–10 connections permanently open and ready. When the app needs the database it borrows one, uses it, and returns it.

backend/db.py — pool setup
# min_size=2: always keep 2 connections open and ready.
# max_size=10: never open more than 10 at once.
_pool = ConnectionPool(
    conninfo=config.DATABASE_URL,
    min_size=2,
    max_size=10
)

Deduplication — the most important design decision

When you re-import the same CSV, or export a CSV that overlaps with a previous one, the database must not create duplicate entries. We solve this with an upsert:

The upsert pattern
INSERT INTO activities (id, start_local, distance_km, ...)
VALUES (...)
ON CONFLICT (start_minute) DO UPDATE SET
    distance_km = COALESCE(excluded.distance_km, activities.distance_km),
    avg_hr      = COALESCE(excluded.avg_hr,      activities.avg_hr),
    ...

start_minute is the run's start time truncated to the minute (e.g. "2026-06-04 07:32"). Since two real runs can never start in the exact same minute, this is a reliable unique key. If a conflict is detected, COALESCE keeps whichever value is not null — so a richer earlier import (with HR data) is never overwritten by a sparser later one.

✅
Result: Importing many overlapping CSVs (thousands of rows across two years) collapses to exactly the genuinely-new activities — currently 873 runs + 280 rides — with no duplicates and no data loss.

One table, two sports — the discriminator pattern

Running and cycling share the same shape (distance, duration, HR, calories, elevation), so they live in one activities table. The only field that differs — pace (min/km) vs speed (km/h) — gets its own column, and a single activity_type column routes each row. Every running query carries WHERE activity_type = 'running' and every cycling query = 'cycling', so the two sports are fully isolated in the UI while sharing all the storage, dedup, and import machinery.

CSV Importer

Garmin exports CSVs in several shapes depending on language and on whether the file was re-saved through (Greek) Excel. The importer detects the actual number/date format from the data itself — not from the header language — then categorises each row as running or cycling.

FeatureRaw export (EN or GR)Greek-Excel re-save
Decimal separator14.32 (period)14,32 (comma)
Date format2026-06-11 17:37:51 (ISO)11/6/2026 17:37
Time format00:35:07 (clean)5:30:00 πμ (time-of-day + πμ/μμ)
Sport metricrunning → Μέσος ρυθμός (pace) · cycling → Μέση ταχύτητα (speed)
⚠️
The trap we avoided: the cycling file had Greek headers but ISO/period numbers. The old header-based detection would have read 14.32 km as 1432 km. Detecting the format from the values fixes this.
backend/csv_importer.py — format detection from data + sport routing
def _detect_excel_greek(rows, header_info):
    # Look at the actual values, not the header language.
    for row in rows:
        # πμ/μμ in a time field ⇒ Excel re-save (comma decimals)
        if any(ch in time_value for ch in ("π", "μ")): return True
        if date_value.startswith("20"):  # ISO date ⇒ raw export
            return False
    return False

def _activity_category(activity_type):
    # 'Ποδηλασία' / 'Cycling' → cycling ; 'Τρέξιμο' / 'Running' → running
    t = activity_type.lower()
    if "ποδηλασ" in t or "cycling" in t: return "cycling"
    if "τρέξιμο" in t or "running" in t: return "running"
    return None  # skip swims, walks, etc.

Synthetic IDs

Garmin's CSV format does not include a unique activity ID (unlike the API). We generate a deterministic ID by hashing the date + distance + duration. The same run always produces the same hash, making re-imports safe. IDs are made negative to distinguish them from real Garmin API IDs (which are positive).

Deterministic ID generation
def _synthetic_id(date_str, distance_km, duration_min):
    payload = f"{date_str}|{distance_km}|{duration_min}".encode()
    h = hashlib.sha256(payload).hexdigest()[:15]  # 60-bit hash
    return -int(h, 16)  # negative = CSV-sourced

Playwright Sync — Browser Automation

Playwright is a browser automation library from Microsoft. It can control Chrome, Firefox, or Edge programmatically — clicking buttons, filling forms, and capturing downloads — exactly as a human user would.

🔒
Why not the official Garmin API? Garmin's developer program is B2B-only — it requires a registered company and a formal application process. For personal use, browser automation against the same website you log into manually is the only stable path.

The persistent profile strategy

A fresh browser profile with no history, no cookies, and no saved preferences looks like a bot to Garmin's login system. We use a persistent profile stored in data/chrome_profile/ that survives between runs. After the first login the session is reused automatically.

backend/garmin_playwright.py — anti-detection
# 1. Use the real Google Chrome installed on your machine (not a downloaded browser)
# 2. Point to a persistent profile directory that builds up history over time
# 3. Pass --disable-blink-features=AutomationControlled so Chrome does NOT
#    set the navigator.webdriver flag that Garmin checks
context = pw.chromium.launch_persistent_context(
    user_data_dir="data/chrome_profile",
    channel="chrome",
    headless=False,
    args=["--disable-blink-features=AutomationControlled"],
)

# 4. Inject JS into every page before it loads — overrides navigator.webdriver
context.add_init_script(
    "Object.defineProperty(navigator, 'webdriver', {get: () => undefined})"
)
🔀
Two sync buttons, one engine. export_activities(sports) exports a CSV for each requested sport in a single browser session. The Running tab's Sync Running button asks for ["running"] (fast); the Cycling tab's Sync from Garmin asks for ["running", "cycling"]. The first sport exports with no extra page reload; only switching to the second sport's filter pays the reload cost — so single-sport syncs stay quick.

The full sync flow

1
Open Chrome → navigate to Garmin activities page page.goto("connect.garmin.com/app/activities?activityType=running")
2
Wait for login (if session expired) Script pauses up to 5 minutes. You log in manually. After login, Garmin redirects to the home page.
3
Navigate back to activities page Detects the post-login redirect and navigates back to the activities URL automatically.
4
Export the first sport (running) Poll up to 45 s for the "Εξαγωγή σε CSV" button (Garmin's React app is slow to render), click it, capture the download → garmin_sync_running_<timestamp>.csv.
5
Switch to cycling view & export (dual sync only) Navigate to ?activityType=cycling, wait for the filtered list to load, export → garmin_sync_cycling_<timestamp>.csv. Each sport is wrapped independently, so one failing never breaks the other.
6
Auto-import each CSV → show count of new workouts Counts activities before and after. The difference is the number of genuinely new runs/rides added.
Waiting for the export button robustly
def _wait_for_export_button(page, timeout=45_000):
    # Try each locale label in turn
    for label in ["Εξαγωγή σε CSV", "Export to CSV", ...]:
        try:
            loc = page.get_by_text(label, exact=True)
            loc.first.wait_for(state="visible", timeout=per_label)
            return loc.first
        except PWTimeoutError:
            continue
    # Fallback: any button or link containing the text "CSV"
    return page.locator("button, a").filter(has_text="CSV").first

Claude AI Integration

We use the Anthropic Python SDK to call Claude in two distinct ways: streaming chat for the coaching conversation, and structured JSON generation for weekly plans.

Streaming chat

The coaching chat uses streaming — Claude sends its response token by token as it generates it, rather than waiting until the full answer is ready. This makes the conversation feel live and responsive, like watching someone type.

backend/routes/chat.py — streaming response
with anthropic_client.messages.stream(
    model="claude-opus-4-7",
    system=f"""You are an expert running coach.
The athlete's recent stats: {stats_summary}
Their current goals: {goals}
Their personal records: {personal_records}""",
    messages=conversation_history,
) as stream:
    for text in stream.text_stream:
        yield text   # each token sent to browser immediately
💡
Context injection: Before calling Claude, we fetch your real activity data from the database and embed it in the system prompt. Claude is not guessing — it is reasoning about your actual 873 runs, your specific goals, and your real personal records.

Weekly plan generation — structured output

For weekly plans we use a structured prompt: we instruct Claude to respond exclusively in a specific JSON format. We then extract the JSON with a regex, validate it has exactly 7 days, and store it in the database.

backend/routes/plans.py — structured JSON prompt
prompt = f"""
Generate a 7-day training plan. Respond ONLY with valid JSON,
no explanation, no markdown fences:
{{
  "week_theme": "...",
  "days": [
    {{
      "day": "Monday",
      "workout_type": "easy",   // easy|tempo|intervals|long|rest|cross
      "title": "Easy recovery run",
      "description": "...",
      "distance_km": 8,
      "duration_min": 50
    }},
    ...  // 7 days total
  ]
}}

Athlete context:
- Total runs: {stats["total_runs"]}, Total km: {stats["total_km"]}
- This week: {stats["this_week_km"]} km
- Goals: {goals_text}
"""

# Extract JSON from response using regex (robust to extra text)
match = re.search(r'\{.*\}', response, re.DOTALL)
plan = json.loads(match.group())

Paste-a-plan → calendar

The same structured-output trick powers a second flow: paste any free-text plan the coach wrote in the chat into the Training Plan tab, and POST /plans/parse sends it to Claude with a "convert this to the 7-day JSON schema" prompt. The result is saved (weekly_plans, tagged source: "chat") and rendered as a Mon–Sun calendar — turning loose prose into a structured, persistent week.

Frontend — HTMX + Chart.js

The entire frontend is a single HTML file — no React, no Vue, no npm install, no build pipeline. For a personal local tool, the simplest approach that works is the correct one.

HTMX — server-rendered interactivity without JavaScript

HTMX is a small library (~14 KB) that lets HTML elements make HTTP requests and swap the server's response into the page — without writing any JavaScript. The server builds the HTML; HTMX handles the swap.

Example: the Running tab's Sync button

  hx-target="#sync-status-run"
  hx-indicator="this">
  Sync Running
</button>
<div id="sync-status-run"></div>

Chart.js — the per-tab charts

Charts use Chart.js 4.4.3 from a CDN. Each tab fetches its /stats/* endpoints in parallel with Promise.all() and renders together. Charts are lazy — each tab initialises only the first time it's opened (separate dashReady / cycReady / goalsReady flags), so nothing loads until you look at it. Running charts are blue/green; cycling charts are purple, so the two sports read differently at a glance.

Lazy chart initialisation
let dashReady = false;

function showTab(id) {
    // Only fetch + render charts the first time Dashboard is opened
    if (id === 'dashboard' && !dashReady) {
        dashReady = true;
        initCharts();
    }
}

async function initCharts() {
    // Fetch all 5 endpoints in parallel
    const [summary, mileage, pace, hr, prs] = await Promise.all([
        fetch('/stats/summary').then(r => r.json()),
        fetch('/stats/weekly-mileage').then(r => r.json()),
        fetch('/stats/pace-trend').then(r => r.json()),
        fetch('/stats/hr-trend').then(r => r.json()),
        fetch('/stats/prs').then(r => r.json()),
    ]);
    // Render charts with the received data...
}

Sleep Tracking & Daily Automation

Sleep is not an activity, so it lives in its own tables and has its own importer and scraper. The interesting parts are (a) Garmin offers three different sleep exports with three different shapes, and (b) the sleep sync runs by itself once a day.

Three export shapes — picking the right two

Garmin viewWhat its CSV containsWe use it for
1 yearone row per week (averages)the long-term backdrop → sleep_weeks
1 dayone night, vertical key→value, with the deep/light/REM breakdownthe daily detail → sleep_nights
7 daysper-night rows, but no stage breakdownnot used
⚠️
The export format depends on the selected view, not just the date range — a subtle trap. The scraper therefore always clicks the correct range tab (1-day) before exporting, and the sleep page's export hides behind a "⋮" menu we open via its exact title="Μενού" button.

The two tables

Parsing the 1-day file (key → value)

Unlike the row-based activity CSVs, the 1-day sleep file is a vertical list of key,value lines in Greek. The parser reads it into a dictionary and converts the localized values — durations like 6ώ 43λ → minutes, and so on.

backend/sleep_importer.py — the per-night parser
def parse_sleep_day(text):
    d = {}
    for line in text.splitlines():
        k, v = line.split(",", 1)        # "Διάρκεια βαθέος ύπνου,59λ"
        d[k.lower().strip()] = v.strip()
    return {
        "night_date":   d["ημερομηνία"],
        "deep_min":     _parse_duration(d["διάρκεια βαθέος ύπνου"]),
        "rem_min":      _parse_duration(d["διάρκεια ύπνου rem"]),
        "hrv_ms":       _parse_int(d["μέσο hrv στη διάρκεια της νύχτας"]),
        ...

The tab leads with nightly detail — a stacked deep/light/REM stage chart, sleep score, and HRV per night — over the weekly averages shown below as a long-term backdrop (so the page isn't empty while nightly data accrues from today).

The hands-off daily sync

The goal: capture last night's sleep once a day, automatically, without clicking. Three pieces make that happen:

1
A guarded sync script — scripts/daily_sleep_sync.py Checks a small state file: if it already synced today, it exits immediately (no browser). Otherwise it exports last night, imports it, and records the date. A failed run isn't recorded, so it simply retries next time.
2
A launcher — scripts/run_sleep_sync.bat A one-line batch file that activates the project's Python and runs the script.
3
A logon trigger — the Windows HKCU\…\Run registry key Windows runs the launcher every time you log on. Task Scheduler would be tidier, but it's locked to admins on this machine, so the per-user Run key is the no-admin path. The once-a-day guard means only the first logon of the day actually opens a browser.
✅
Net effect: the first time you log on each day, a browser quietly opens for ~10 seconds, pulls last night's sleep (stages, HRV and all), saves it, and closes — with no action from you. Every 14 days, the same session also re-exports the 1-year weekly file so the long-term trend stays current (the nightly file lacks sleep-need and bed/wake times, so the weekly export is the only way to keep those charts alive). Both cadences share one guard each, so nothing ever runs more than it should. Everything is logged to data/sleep_sync.log, and it's installed or removed with the two PowerShell scripts.
