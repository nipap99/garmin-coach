## 2. Proposed folder structure

Rule: **the three entry points stay where they are** (`daily_sync.py`, `fitness_report.py`, `mcp_coach.py`). The Windows task, Claude Desktop's MCP config and the Sunday prompt all point at those paths, so moving them would break things.

├─ start_app.bat           ← open the dashboard

├─ fitness_report.py       ← JOB: Sunday PDF                   (Claude Desktop task)
├─ mcp_coach.py            ← Claude's window into the data     (Desktop, report, run-analyst)
├─ requirements.txt  .env  .env.example  .gitignore  LICENSE
│
├─ backend/                ← DATA LAYER (Python, deterministic, $0)
│   ├─ config.py  db.py  garmin_api.py  main.py
│   ├─ training_load.py
│   ├─ metrics.py          ← NEW: weekly km, hard/easy days, plan adherence, paces
│   ├─ coach_tools.py      ← the MCP tool functions (moved out of the dead coach.py)
│   ├─ csv_importer.py     ← kept: manual CSV upload in the app
│   ├─ nutrition.py        ← food library + logging (AI chat part removed or swapped — see §4)

├─ coaching/               ← THE COACH'S BRAIN (plain text, edit freely)
│   ├─ coaching_rules.md   ← single source: template, volume rules, nutrition stance, goals

├─ frontend/index.html     assets/ (fonts, icon)

The two 800 MB folders (`chrome_profile`, `ms-playwright`) are only cache, so they'd be **deleted**, not archived. Everything else goes to `_archive/` first. You can empty it in a month if nothing is missed.

## 3. Who does what: data vs coaching vs report

Today the line between them is blurry. Claude gets raw rows and has to do the counting. Proposed split:

| Layer | Job | Who | Cost |
|---|---|---|---|
| **1. Data** | Sync, store, and **compute every number**: Mon–Sun weekly km, laps merged into sessions, hard/easy classification, ACWR, efficiency, HRV vs baseline, plan adherence, current paces from recent results | Python (`daily_sync.py`, `backend/metrics.py`) | $0 |
| **2. Coaching** | Judgment only: is the week good, what to change, next week's plan. Reads **pre-computed summaries** through MCP, writes `report_ai.json` | Claude on the subscription (Sunday task, run-analyst, Desktop chat), all following `coaching/coaching_rules.md` | $0 |
| **3. Presentation** | Draw the PDF from DB + `report_ai.json`; dashboard shows the same numbers live | Python (`fitness_report.py`, FastAPI) | $0 |

What this changes in practice:
- **New MCP tool `week_summary(week_start)`.** It returns each day of a Mon–Sun week as one session (laps merged), with km, pace, HR, a hard/easy flag, the planned session from last Sunday's report, and a ✓/✗. Claude stops adding laps, and the Sunday report and run-analyst agree because they read the same numbers.
- **`training_load` switches to Mon–Sun weeks**, so it matches everything else.
- **One rules file.** SKILL.md, run-analyst and the MCP instructions all say "read `coaching/coaching_rules.md`" and no longer carry their own copies. Change your plan once and every coach follows it.
- **Each Sunday plan is saved to the DB** (the existing `weekly_plans` table). The dashboard's "Today" card shows the real session for today, and next week's review can score the plan against what you actually ran.
- Fewer tokens per report, so the Sunday run is faster and stays well within Pro limits.

## 4. Coaching upgrades: pick the ones you want

Each one is grounded in something your data showed this week.

| # | Upgrade | What it does | Why (your data) | Effort |
|---|---|---|---|---|
| **A** | **Plan vs. actual scoring** | Every report opens with "Planned / Done / Δ" per day plus an adherence %, and the coach adapts: if Thu keeps turning into intervals, it asks why or reshapes the week | Thu and Sat drifted for 2+ weeks; no long run since Oct 24 | Medium (needs §3) |
| **B** | **Auto-updated training paces** | Paces recalculated each week from your best recent efforts (time trials, races, steady tempos) using a VDOT-style calculator; goal paces stay separate | Library says 5k 3:55/km; you ran 3:35/km on Nov 8, so all prescribed paces are ~10–20 s/km too slow | Small |
| **C** | **Morning readiness light** | Daily green/amber/red from last night's HRV vs your 7-day baseline + resting HR, shown on the dashboard "Today" card with the planned session. Amber = do it easier; red = swap for easy | HRV fell 100–105 → 81–89 in a week with flat load; you'd see it the morning it happens, not on Sunday | Small |
| **D** | **Long-run guardrail** | Flags when no run ≥ 16 km for 2 weeks, and protects Saturday's long run in the plan (moves the 5k test to another day instead of replacing the long run) | Long run replaced by 5k efforts on Nov 7 and Nov 14 | Small |
| **E** | **Block counter (4-week cycles)** | System knows "week 2 of 4", so cutbacks (−25–30%) happen automatically every 4th week and the report says so | Template asks for it, nothing tracks it today | Small |
| **F** | **Real goals in the DB** | You set 1–3 real targets (e.g. 5k sub-18:00 by spring); coaches stop using placeholders, report shows a countdown and predicted time vs target | `goals` is empty | Tiny (you decide the targets) |
| **G** | **Total load incl. cycling for fatigue** | run-analyst and the report judge fatigue from runs + rides (rides are ~40% of your load); running km still judged separately for running volume | Agent currently can't see rides | Tiny |
| **H** | **Food logging through Claude chat ($0)** | Replace the paid food-photo chat with a `log_food` MCP tool, so you send a food photo in the Claude app (subscription) and it logs to the same DB. Makes the MCP server write to one table (food_log) | Removes the last paid path while keeping photo logging | Small |

My recommendation: **B + C + D + F first** (small, high value). Then do **§3 + A**, which is the real "smarter coach" step. Add **H** if you still want photo food logging; otherwise just drop the food chat.
